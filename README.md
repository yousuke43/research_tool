# Decision Table Experiment Tool

要求仕様から

1. 1つの抽出モデルで **Decision Items** を抽出
2. 同じ Requirements と同じ Decision Items を **複数の生成モデル** へ渡して **Decision Table** を生成

を一度の「実行」でまとめて行う、研究実験用の Windows デスクトップアプリ (PySide6) です。
LLM の呼び出しはすべて OpenRouter API 経由で行います。

生成結果は「比較」タブで、同じ条件の組み合わせに対してモデルごとの結果が
食い違っていないかを自動検出・ハイライト表示できます (詳細は後述)。

## 1. Python 環境の準備

Python 3.10 以上 (開発確認は 3.13) が必要です。

```powershell
cd C:\Users\yousu\research\tool\tool
python -m venv .venv
.\.venv\Scripts\Activate.ps1
```

## 2. 必要パッケージのインストール

```powershell
pip install -r requirements.txt
```

インストールされるもの: `PySide6` (GUI) / `requests` (HTTP) / `python-dotenv` (.env 読み込み)

## 3. OpenRouter API キーの設定

[https://openrouter.ai/keys](https://openrouter.ai/keys) でキーを発行し、
プロジェクト直下の `.env` に書きます (`.env.example` がひな形です)。

```
OPENROUTER_API_KEY=sk-or-v1-xxxxxxxx
```

キーが未設定のまま実行すると、その旨のエラーダイアログが出ます。
`.env` は Git 管理対象外です (`.gitignore`)。

> Windows のシステム環境変数に `OPENROUTER_API_KEY` を設定している場合は、そちらが優先されます
> (`.env` は既存の環境変数を上書きしません)。

## 4. アプリの起動

```powershell
python main.py
```

ブラウザは使いません。通常の Windows デスクトップアプリとして起動します。

## 5. OpenRouter からのモデル取得

- 起動時にバックグラウンドでモデル一覧を自動取得します (GUI は固まりません)。
- 明示的に取り直す場合は **モデル設定... → 「モデル一覧を更新」**。
- 取得した一覧は `config/models_cache.json` にキャッシュされ、次回起動直後の表示に使われます。
- 取得に失敗した場合はエラーメッセージを表示し、キャッシュがあればそれを使って動作を続けます
  (アプリは落ちません)。
- モデル一覧はコードにハードコードしていません。

## 6. 抽出モデル・生成モデルの設定

メイン画面の **「モデル設定...」** を押すと設定ダイアログが開きます。

- 左: **抽出モデル** — Decision Items 抽出に使うモデルを 1 つ選択
- 右: **生成モデル** — Decision Table 生成に使うモデルをチェックボックスで複数選択
- 上部の検索欄で、表示名 / Model ID による絞り込みができます
- 一覧には **表示名** と **OpenRouter model ID** の両方を表示します

選択内容は `config/settings.json` に保存され、次回起動時に復元されます。

```json
{
  "extraction_model": "openai/gpt-4o",
  "generation_models": [
    "openai/gpt-4o",
    "anthropic/claude-sonnet-4",
    "google/gemini-2.5-pro"
  ]
}
```

保存済みのモデルが OpenRouter 上に見つからない場合は、メイン画面と設定ダイアログに
「⚠ OpenRouter 上に見つからないモデル: ...」と赤字で表示します。

## 7. 実験の実行

1. **Requirements** 欄に要求仕様を入力
2. **実行** を押す

以降は自動で次の順に進みます。ボタンは 1 つだけです。

```
Requirements
  → 抽出モデルで Decision Items を抽出 (実験につき 1 回だけ)
  → 同じ Requirements + 同じ Decision Items を各生成モデルへ
  → 各モデルの Decision Table を生成 (最大 4 並列)
  → 画面へ表示
  → outputs/ へ保存
```

- 処理状況は画面下部の「処理状況」とステータス欄に逐次表示されます
  (例: `Decision Items 抽出中...` → `GPT-4o で生成中...` → `生成完了: ...` → `完了`)。
- 結果はタブで表示されます。並びは次の通りで、開いたときは **「比較 (縦)」** が表示されます
  (詳細は「12. 結果の比較」)。
  1. **比較 (縦)** — 同じ条件の組み合わせごとに、各モデルの結果を上下に並べて比較
  2. **テーブル一覧 (縦並び)** — 各モデルの Decision Table を加工せずそのまま縦に並べたもの (人手での見比べ用)。
     R1, R2… の列見出しをつかんでドラッグすると列を並び替えられる (区分・記述は固定。「R列の並びを元に戻す」で全表を元に戻せる)
  3. **Extracted Decision Items**
  4. モデルごとのタブ (「プレビュー / Markdown ソース」切り替え・「コピー」あり)
  5. **比較 (横)** — 従来の比較タブ (組み合わせ×モデルを横に並べる)
- 生成に失敗したモデルのタブは `⚠` 付きで表示され、`API Error: ...` を確認できます。
  1 つ失敗しても、他のモデルの結果は表示・保存されます。
- Decision Items の抽出自体に失敗した場合は、生成へ進まずエラーダイアログを表示します。

## 8. プロンプトの変更

プロンプトは Python コードではなく `prompts/` のテキストファイルで管理しています。
アプリは実行のたびに読み直すので、**再起動なしで差し替えられます**。

| ファイル | 用途 | 使えるプレースホルダ |
| --- | --- | --- |
| `prompts/extract.txt` | Decision Items 抽出 | `{requirements}` |
| `prompts/generate.txt` | Decision Table 生成 (従来方式) | `{requirements}` `{decision_items}` |
| `prompts/generate_framework.txt` | 動作結果の補完 (新方式) | `{requirements}` `{decision_items}` `{rule_table}` `{output_example}` |
| `prompts/additional_description.txt` | 追加記述案の生成 | `{document}` `{difference}` |

プレースホルダを削除するとエラーになります (要求仕様が送られない事故を防ぐため)。

## 9. 実験結果の保存場所

1 回実行するごとに `outputs/<実行日時>/` が作られ、自動保存されます
(dataフォルダ一括実行の場合は `outputs/batch_<日時>/<仕様ファイル名>_<実行日時>/`。詳細は次節)。

```
outputs/
  20260916_140530/
    input.txt                                    入力した Requirements
    decision_items__anthropic_claude-haiku-4.5.txt  抽出された Decision Items (ファイル名で抽出モデルがわかる)
    openai_gpt-4o.md                              各生成モデルの Decision Table (失敗時はエラー内容)
    anthropic_claude-sonnet-4.md
    google_gemini-2.5-pro.md
    results.json                                  実行日時・使用モデル・所要時間・トークン数・全結果をまとめたもの
```

ファイル名はモデル ID から生成します (`/` などは `_` に置換)。
`results.json` には抽出・各生成モデルそれぞれの `elapsed_sec` (所要時間) と
`prompt_tokens` / `completion_tokens` / `total_tokens` (トークン数) が記録され、
どのファイルがどのモデルの出力かも `output_file` で対応付けられます。
データベースは使いません。メイン画面の「出力フォルダを開く」で保存先を開けます。

## 10. dataフォルダの一括実行

複数の要求仕様をまとめて実行したい場合は、`data/` フォルダに仕様を
`.txt` ファイルとして置き、メイン画面の **「一括実行 (dataフォルダ)...」** を押します。

- ダイアログに `data/` 内の `.txt` ファイルが一覧表示されるので、実行したいものだけ
  チェックして「実行」を押します (「すべて選択」「選択解除」も使えます)。
- 使用するモデルはメイン画面の「モデル設定...」で選択済みのものがそのまま使われます。
- 各仕様ごとに (抽出 → 各生成モデルで並列生成 → 保存) を行います。
  仕様どうしも **「同時に実行する仕様の数」(既定 3、最大 8)** だけ並列に実行します
  (1 にすると従来どおり1件ずつ順番)。同時に送るリクエスト数は「この値 × 生成モデル数 (最大4)」なので、
  OpenRouter のレート制限 (HTTP 429) でエラーが出る場合は値を下げてください。
- 1件の抽出・生成に失敗しても処理は中断せず、他の仕様は続行します。
  閉じて中断した場合、まだ始まっていない仕様は実行されません (処理中のものは最後まで行います)。
- 一括実行1回分の結果は **`outputs/batch_<一括実行の開始日時>/` の下にまとめて** 保存されます。
  ```
  outputs/
    batch_20261118_110156/
      batch_summary.json                実行した仕様・成否・保存フォルダ名・使用モデルの一覧
      sample_parking_20261118_110156/   仕様ごとのフォルダ (中身は手動実行と同じ構成)
      01_テーマパーク_変数追加版_あり_20261118_110157/
  ```
  「過去の結果を見る」にも表示されます (一覧に `(一括: batch_...)` と付きます)。

### Excel (.xlsx) からの一括実行

`data/` に `.xlsx` を置くと、**1行 = 1件** として一覧に表示されます。

- ヘッダーに `番号` `区分` `テーマ` `内容` `解釈揺れ` `実行` の列があるシートだけを読み込みます
  (列の順番は自由。列がそろっていないシートは読み飛ばします)。
- 実行対象は「区分」が `変数追加版` で始まり、かつ「実行」列に `〇` が入っている行です。
- モデルに渡すのは「内容」列だけです。番号・区分・テーマ・解釈揺れ・揺れの内容・シート名・行番号は
  `results.json` の `source_meta` に記録します。
- 保存先は `outputs/batch_<日時>/<番号>_<テーマ>_変数追加版_<解釈揺れ>_<実行日時>/` です
  (例: `01_テーマパーク_変数追加版_あり_20261029_153000/`)。実行日時が付くので、再実行しても前の結果は残ります。
- 読み込み処理は `utils/excel_specs.py` にあります。列名や対象の区分を変える場合はファイル先頭の定数を変更してください。

## 11. 過去の実行結果を見る

メイン画面の **「過去の結果を見る...」** を押すと、`outputs/` 以下に保存済みの
実行結果 (手動実行・一括実行どちらも) を一覧から選んで、実行直後と同じ
タブ形式 (比較 (縦) + テーブル一覧 + Extracted Decision Items + モデルごと + 比較 (横)) で再表示できます。
各タブには所要時間とトークン数も表示されるため、モデル間の比較・分析がしやすくなっています。

## 12. 結果の比較 (比較タブ)

実行直後の画面・過去の結果画面のどちらにも、全モデルの Decision Table を横断比較する
**「比較 (縦)」「比較 (横)」** タブがあります。計算内容は同じで、並べ方だけが違います。

- **比較 (縦)**: 通常のデシジョンテーブルと同じく条件を行に並べ、1列 = 1組み合わせ。
  条件の行は1つずつで、動作 (結果) の行だけをモデルの数だけ縦に並べる
  (`[動作] 入場料金 / GPT-4o` のように)。同じ列を上から下へ見ればモデル間の違いがわかる。
  1つのモデルの複数ルールが同じ組み合わせに入った場合は `4250 / 4500` のように並べて表示する。
- **比較 (横)**: 1列 = 組み合わせ×モデル。従来の表示。

「表記ゆれの解決」の統合はタブごとに独立しています (縦で統合しても横には反映されません)。

比較タブ上部の **「比較対象:」** のチェックを外すと、そのモデルを比較から外せます
(食い違いの判定・組み合わせ数・追加記述案の候補からも外れます)。この設定は縦・横の両方の比較タブに反映されます。

やっていることは次の通りです。

1. 各モデルの Markdown 表 (`区分 | 記述 | R1 | R2 ...`) を条件部・動作部の行に分解する。
2. **条件・動作の「記述」を正規化して対応付ける**
   (空白・改行の差異は無視するので、`会員である` と `会員  である` は同じ項目として扱われる)。
3. 全モデルに共通する条件の **組み合わせ単位** でルールをグループ化し、
   同じ組み合わせなのに **動作・結果の値がモデル間で食い違っているセルを赤くハイライト**する。
   あるモデルがその組み合わせのルールを生成していない場合はグレー表示になる。

### 表記ゆれがあって自動対応付けできない場合

モデルによって条件・動作の表記が微妙に違う (例: 「会員である」 vs 「会員ユーザーである」) ため
正規化だけでは対応付けられない項目は、比較タブ上部の **「表記ゆれの解決」** パネルに
一覧表示されます。そこから該当する項目を複数選択して
**「選択した項目を同じ項目として統合する」** を押すと、表示名を1つ入力するだけで
以後は同じ項目として扱われ、2. 以降と同じロジックで比較できるようになります。
統合は「統合をすべて解除」でいつでも取り消せます。

### その他

- 「結果が異なる組み合わせのみ表示」にチェックすると、一致している組み合わせを隠して
  差分のある組み合わせだけに絞り込めます。
- 比較対象は生成に成功し、かつ Markdown 表として解析できたモデルのみです。
  生成失敗・解析不能なモデルは比較対象外としてタブ上部に明示されます。
- 比較できるモデルが2つ未満の場合は、その旨のメッセージが表示されます。

### 追加記述案の作成 (解釈の分かれを解消する記述を LLM に提案させる)

比較タブ右上の **「追加記述案を作成...」** から、解釈が分かれている箇所について
「それぞれの解釈に一意に定まるような追加記述」を LLM に提案させられます。

1. **差異の指定** (ダイアログ上部のプルダウン)
   - `比較表で選択: 組合せN` — 比較表でセル (列) を選択してからボタンを押すと、その組み合わせが選ばれた状態で開く
   - `自動検出: 組合せN` — モデル間で結果が食い違った組み合わせ (赤いセル) が自動で並ぶ
   - `手動: <モデル> の Rn をひな形にする` — 任意のルール列の条件・結果を読み込み、もう1つの解釈を自分で書き足す
     (モデルが1つだけの実行でも使える)
   - `手動: 自由入力` — 条件・解釈をすべて自分で書く
2. 条件 (1行1つ) と分かれた解釈 (結果動作) は編集でき、編集すると次の文章が自動で組み立てられます。
   文章そのものを直接書き換えてもかまいません。
   ```
   条件が「来場人数が1人である（成立）、来場した団体が全員学生である（成立）」の時に、結果動作が「入場料金：4750」と「入場料金：4250」になる。
   ```
3. モデルを選んで **「追加記述案を生成」** を押すと、元の文書 (Requirements) とこの文章が LLM に渡され、
   `「入場料金：4750」に対応した記述：…` の形式で追加記述案が返ってきます。
4. 結果はその実行結果フォルダの `additional_descriptions/` に自動保存されます。
   - `<生成日時>__<モデルID>.md` — 差異の文章・各解釈をとったモデル/ルール・追加記述案
   - `<生成日時>__<モデルID>.json` — 上記 + 元の文書・トークン数・所要時間

プロンプトは `prompts/additional_description.txt` (プレースホルダ: `{document}` `{difference}`) で、
他のプロンプトと同じく再起動なしで差し替えられます。処理本体は `services/additional_description_service.py`、
画面は `ui/additional_description_dialog.py` です。

### 実装の場所 (拡張する場合)

| ファイル | 役割 |
| --- | --- |
| `models/decision_table.py` | パース結果 (`DecisionTable` / `DecisionRow`) と入力 (`TableSource`) のデータ構造 |
| `services/decision_table_parser.py` | モデル出力の Markdown 表を `DecisionTable` へ変換 (Qt非依存) |
| `services/table_comparison.py` | ラベルの正規化・対応付け・組み合わせ単位の比較ロジック本体 (Qt非依存、純粋関数ベース) |
| `ui/comparison_view.py` | 比較タブの描画とユーザー操作 (表記ゆれの手動統合など) |

比較の計算ロジックはすべて `services/table_comparison.py` にあり、Qt に依存しないため
単体で動作確認・拡張がしやすい構成になっています。

## 13. 生成方式 (従来方式 / 新方式: 共通DT枠組み)

メイン画面の実行ボタン左、および一括実行ダイアログの **「生成方式」** で選びます (選択は settings.json に保存)。

| 方式 | 内容 |
| --- | --- |
| 従来方式 | 各生成モデルが Decision Table 全体 (条件部も) を Markdown で生成する。これまでと同じ |
| 新方式 (共通DT枠組み＋動作結果補完) | 条件の組合せをプログラムで作り、全モデルに同じ枠組みを渡して **動作結果だけ** を JSON で返させる |

新方式の流れ:

```
Requirements
  → 抽出モデルで条件項目・動作項目を抽出 (従来と同じ prompts/extract.txt)
  → 条件 n 個の Y/N 全組合せ 2^n 通りをプログラムで生成 (LLM は使わない)
      - 論理的に成立しない組合せも残す / '-' による統合はしない
      - 条件列の順序とルールID (R1 = 全て Y … 最後 = 全て N) を固定
  → 全生成モデルに「要求仕様 + 抽出項目 + 同じ条件組合せ」を渡す (prompts/generate_framework.txt)
  → 各モデルは {"results": [{"rule_id": "R1", "actions": {"最終料金": 3750}}, ...]} だけを返す
  → JSON を検証 (ルールIDの欠落・重複・未定義、動作項目の欠落・未定義、型、JSON 解析失敗)
      - 検証に失敗したモデルは「形式不正」として失敗扱い (不完全な DT を正常結果にしない)
  → 枠組みに動作結果を埋め込み、従来と同じ Markdown DT として保存・表示
  → 同じルールIDどうしでモデル間の動作結果を比較
```

- 成立しない組合せには「適用不可」を返させます。「適用不可」の意味的な正しさは JSON 検証の対象外です。
- 数値型に `"4,500"` のような数字だけの文字列が返った場合は数値に変換し、警告として記録します
  (`"不明"` などは型不正としてエラー)。
- 条件数が上限 (既定 6) を超える場合は警告を出し、共通DTは生成しません (抽出結果は保存します)。
- ルール数がバッチサイズ (既定 64) を超える場合は、ルールを複数バッチに分けて生成し最後に統合します
  (バッチ間でもルールIDと条件組合せは固定)。

### 枠組みを確認してから生成する (2段階実行)

一括実行ダイアログで生成方式に「新方式」を選ぶと **実行モード** を選べます (既定は ①)。

| 実行モード | 内容 |
| --- | --- |
| ① 枠組みの作成のみ | 抽出して共通DT枠組みを作り、`frameworks/` に **下書き** として保存する。生成モデルは呼ばない |
| ② 承認済みの保存枠組みで生成 | 各仕様の **最新の承認済み枠組み** を全生成モデルに渡す。抽出はしない。承認済みがない仕様は実行しない |
| 抽出から生成まで続けて実行 | 確認なしで一度に実行 (これまでの動作) |

手順:

1. 一括実行で「① 枠組みの作成のみ」→「枠組みを作成」
2. メイン画面の **「共通DT枠組み...」** (または一括実行ダイアログの「枠組みを確認...」) で、
   仕様ごとの条件項目・動作項目・条件組合せ表を確認し **「承認する」**
   - 確認時の気づきは「メモ」に保存できます (生成結果の results.json にも記録されます)
   - 抽出項目に誤りがあれば「抽出項目 (修正)」タブで JSON を直し **「修正内容で新しい版を作成」**。
     元の版は残り、新しい版は `edited: true` / `parent_id` 付きで保存されます
3. 一括実行で「② 承認済みの保存枠組みで生成」。一覧には各仕様の枠組みの状態
   (✔ 承認済み枠組みあり / 未承認の枠組みあり / 枠組みなし) が表示されます

枠組みと仕様の対応:

```
frameworks/
  01_テーマパーク_変数追加版_あり/          仕様名ごとのフォルダ
    20261118_150000_a1b2c3.json            枠組み本体 (機械可読)
    20261118_150000_a1b2c3.md              確認用 (仕様情報・要求仕様・条件一覧・条件組合せ表)
```

JSON には仕様名・Excel の元情報 (ファイル・シート・行・番号・テーマ・解釈揺れ・揺れの内容)・
要求仕様の本文とその SHA-256・抽出モデル・抽出の生出力とトークン数・抽出プロンプト・状態・承認日時・メモを記録します。
生成時は **仕様名と要求仕様本文の SHA-256 が一致する承認済み枠組み** だけを使うので、
枠組みを作った後に Excel の本文を書き換えた場合、古い枠組みは使われません (確認画面に ⚠ が出ます)。
生成結果の `results.json` には `framework_source` (framework_id・承認日時・修正版か・メモ) が残ります。

### 条件組合せの一括除外

「共通DT枠組み...」の **「条件組合せの除外」** タブで、論理的に成立しない組合せを LLM に渡す前に除外できます。

1. 「パターンを追加」(または「パターン: `N Y -`」と理由を入力して「文字で追加」、
   プレビューで選んだ組合せから作成) で除外パターンを登録する。各条件は `Y` / `N` / `-` (どちらでもよい)
2. いずれかのパターンに一致した組合せが除外される。プレビューに
   「全 8 通り → 除外 4 通り → 残り 4 ルール」と、組合せごとの状態 (残す / 除外 #番号) が表示される
   (「除外対象のみ」「残る組合せのみ」で絞り込み可。各パターンの一致数も表示)
3. 理由を入力して **「除外を保存」**。下書きの枠組みはその場で更新、承認済みの枠組みは新しい版 (下書き) を作る
4. 確認して承認 → 「② 承認済みの保存枠組みで生成」で、残した組合せだけを全生成モデルに共通して渡す

例: 条件 C1「来場回数3回以上」C2「来場回数5回以上」C3「来場回数10回以上」に
`N Y -` (5回以上なら必ず3回以上) と `- N Y` (10回以上なら必ず5回以上) を登録すると、8 通り → R1, R2, R4, R8 の 4 通りになる。

- **ルールIDは振り直さない** (除外後も R1, R2, R4, R8)。除外パターンを変えてもIDの意味が変わらないので、
  版・仕様をまたいで比較できる。ルールIDが連番でない場合、プロンプトには「表にあるルールIDだけを出力」と明記する
- **除外は「適用不可」と区別して記録する**: 除外した組合せは LLM に渡さず、比較タブ・CSV では「除外 (LLM未使用)」と理由を表示する。
  LLM が「適用不可」と判断した組合せは、従来どおり各モデルの値として記録される
- 除外パターンと理由は枠組みの JSON (`exclusions`、条件文つき) に保存される。
  「他の枠組みの除外を再利用」で、条件文が対応する別の枠組み (例: 同じ番号の「あり」と「なし」) のパターンを読み込める。
  抽出項目を修正して新しい版を作るときも、条件文で対応付けて引き継ぐ (対応しないパターンは警告を出して引き継がない)
- 除外によって残りのルール数が上限 (2^条件数の上限。既定 64) 以下になれば、7 条件以上の仕様も生成できる
  (除外の編集で列挙できるのは 12 条件 = 4096 通りまで。プレビューは数千通りでも軽く表示される)
- **注意**: 除外するのは条件間の包含・排他などで論理的に成立しない組合せだけにしてください。
  割引の併用可否など、解釈によって結果が変わりうる組合せは研究対象なので除外しないでください (画面にも表示しています)

### LLM に渡すもの・返ってくるもの (具体例)

各段階で LLM (OpenRouter) に何を送り、何が返り、ツールがそれをどう扱うかを、次の小さな仕様で示します。
以下のプロンプト・表・検証結果は、ツールのコード (`services/dt_framework.py` など) で実際に組み立てたものです
(LLM の応答だけは説明用に用意した例)。

```
テーマパークの入場料金は1人5000円とする。会員の場合は入場料金を10%割引する。
来場回数が5回以上の場合はさらに500円引きする。来場回数が10回以上の場合は記念品を渡す。
```

**前提: LLM へのリクエストの形**

どの段階でも、送るのは **1つの user メッセージ (プレーンテキスト) だけ** です。system メッセージ・temperature・
`response_format` は送りません。`max_tokens` は新方式の生成だけ既定で 32000 を送ります。

```json
{
  "model": "openai/gpt-4o",
  "messages": [{"role": "user", "content": "<プロンプト全文 (下記)>"}],
  "max_tokens": 32000
}
```

プロンプト全文は `prompts/*.txt` のテンプレートの `{requirements}` などを単純置換したものです。
**ファイル (.md / .json) を添付しているわけではありません。** 表は Markdown の表、項目は JSON として本文に埋め込まれます。

| 段階 | LLM を呼ぶか | 送るもの | 返ってくるもの |
| --- | --- | --- | --- |
| ① 枠組みの作成のみ | 抽出モデル 1 回 | `extract.txt` + 要求仕様 | 条件項目・動作項目の JSON |
| (条件組合せの作成・除外・確認・承認) | **呼ばない** | — | — (プログラムと人が行う) |
| ② 承認済みの保存枠組みで生成 | 生成モデルごとに 1 回 (バッチ分割時は複数回) | `generate_framework.txt` + 要求仕様 + 抽出項目 JSON + 条件組合せの Markdown 表 + 出力例 | 各ルールの動作結果の JSON |

#### 段階①: 抽出 (抽出モデル)

送るもの: `prompts/extract.txt` の `{requirements}` の位置に要求仕様の本文を入れたもの。

```
あなたは、要求仕様からデシジョンテーブルに必要な項目を抽出する専門家です。
…
### 要求仕様

テーマパークの入場料金は1人5000円とする。会員の場合は入場料金を10%割引する。…

### 条件部
…(以下 extract.txt の固定文。出力形式の JSON 例まで)
```

返ってくるもの (例):

````
```json
{
  "conditions": ["会員である", "来場回数が5回以上である", "来場回数が10回以上である"],
  "actions": [
    {"name": "最終料金", "type": "value", "valueType": "int"},
    {"name": "記念品を渡す", "type": "action"}
  ]
}
```
````

ツールの処理 (ここから先は LLM を使わない):

1. ```` ```json ```` の囲みや前後の説明文を取り除いて JSON を読み、条件・動作項目が空でないか、
   `type` / `valueType` が正しいか、動作項目名が重複していないかを検査
2. 条件 3 個 → Y/N の全組合せ 2^3 = 8 通りを作る (R1 = YYY … R8 = NNN)
3. `frameworks/<仕様名>/<id>.json` と確認用の `.md` に **下書き** として保存

#### 確認・承認 (LLM は呼ばない)

「共通DT枠組み...」で上の 8 通りを確認し、例えば除外パターン `- N Y`
(理由:「10回以上なら必ず5回以上」) を登録すると、R3 (YNY) と R7 (NNY) が除外されて 6 ルールが残ります。
抽出項目を手で直した場合は、以降は直した後の項目が使われます。最後に「承認する」。

`frameworks/` の `.md` は **人が確認するためのファイル** で、LLM には送りません。
LLM に送るのは、次の②で JSON から組み立て直したプロンプトです。

#### 段階②: 動作結果の補完 (全生成モデルに同じ文面)

送るもの: `prompts/generate_framework.txt` に次の 4 つを埋め込んだもの。

| プレースホルダ | 中身 | 形式 |
| --- | --- | --- |
| `{requirements}` | 要求仕様の本文 (枠組み作成時のもの) | プレーンテキスト |
| `{decision_items}` | 承認済み枠組みの抽出項目 (修正版なら修正後)。囲み記号を除いて整形し直したもの | JSON |
| `{rule_table}` | 条件の一覧と、除外後に残ったルールの Y/N 表 | Markdown の表 |
| `{output_example}` | 返してほしい JSON の形 (先頭 2 ルール分) | JSON |

実際に送られるプロンプト (固定文の一部を「…」で省略):

```
あなたは、要求仕様をもとにデシジョンテーブルの動作結果を判断する専門家です。
…
### Requirements

テーマパークの入場料金は1人5000円とする。会員の場合は入場料金を10%割引する。来場回数が5回以上の場合はさらに500円引きする。来場回数が10回以上の場合は記念品を渡す。

### Extracted decision items

{

    "来場回数が5回以上である",

### 共通デシジョンテーブルの条件組合せ

各ルールの条件の値は次のとおりです。`Y` はその条件が成立する、`N` は成立しないことを表します。

条件の一覧:

| ID | 条件 |
|---|---|
| C1 | 会員である |
| C2 | 来場回数が5回以上である |
| C3 | 来場回数が10回以上である |

判断するルール (6 件。ルールIDは連番ではありません。表にあるルールIDだけを出力してください):

| ルール | C1 | C2 | C3 |

| R4 | Y | N | N |
| R5 | N | Y | Y |
| R6 | N | Y | N |

### 判断の手順
…(固定文: 成立しない組合せは「適用不可」、曖昧でも1つの解釈を選ぶ、など)

### 出力形式

次の形式の JSON のみを出力してください。JSON 以外の文章、説明、前置き、後書きは出力しないでください。

{
  "results": [
    {
      "rule_id": "R1",
      "actions": {

```

- 除外した R3・R7 はプロンプトに一切含まれません。
- ルールが 1 リクエストあたりのルール数 (既定 64) を超える場合は、`{rule_table}` と `{output_example}` の
  ルール行だけを分けて複数回送ります (要求仕様と抽出項目は毎回同じ)。

返ってくるもの (例):

```json
{"results": [
  {"rule_id": "R1", "actions": {"最終料金": 4000, "記念品を渡す": "X"}},
  {"rule_id": "R2", "actions": {"最終料金": 4000, "記念品を渡す": "-"}},
  {"rule_id": "R4", "actions": {"最終料金": 4500, "記念品を渡す": "-"}},
  {"rule_id": "R5", "actions": {"最終料金": "4,500", "記念品を渡す": "X"}},
  {"rule_id": "R6", "actions": {"最終料金": 4500, "記念品を渡す": "-"}},
  {"rule_id": "R8", "actions": {"最終料金": 5000, "記念品を渡す": "-"}}

ツールの処理:

1. JSON を検証する。この例は合格で、警告が 1 件だけ出る:
   `R5「最終料金」: 文字列 '4,500' を整数に変換しました`
   - 不合格になる例: R8 が無い (`ルールID が不足しています (1 件): R8`)、除外した R7 を返した
     (`除外したルールID R7 が含まれています (渡していないルール)。`)、`"最終料金": "不明"` (int 型ではない)、
     動作項目名を変えた、JSON として読めない、など。1 件でもあればそのモデルは「形式不正」
2. 生の応答は `raw_responses/<モデル>.txt`、検証後の値は `results.json` の `validated_results` に保存
3. 枠組みに値を埋め込み、従来方式と同じ形の Markdown DT (`<モデル>.md`) を作る:

```
| 区分 | 記述 | R1 | R2 | R4 | R5 | R6 | R8 |
|---|---|---|---|---|---|---|---|
| 条件部 | 会員である | Y | Y | Y | N | N | N |
| 条件部 | 来場回数が5回以上である | Y | Y | N | Y | Y | N |
| 条件部 | 来場回数が10回以上である | Y | N | N | Y | N | N |
| 動作部 | 最終料金 | 4000 | 4000 | 4500 | 4500 | 4500 | 5000 |
| 動作部 | 記念品を渡す | X | - | - | X | - | - |
```

4. 全モデル分そろったら、同じルールIDどうしで値を比較する (共通DT比較タブ)。

参考: **従来方式** の生成では、`prompts/generate.txt` に要求仕様と **抽出モデルの生の出力** (```` ```json ```` の囲みも含む)
を埋め込んで送り、各モデルが条件部も含めた Markdown の DT を自由に書いて返します。

### 新方式の結果画面

従来のタブに加えて、先頭に次の2つが追加されます。完成した DT は従来と同じ Markdown なので、
「比較 (縦)」「比較 (横)」「テーブル一覧」「追加記述案を作成...」もそのまま使えます。

- **共通DT比較** — 1行 = 1ルール。各モデルの動作結果を並べ、次の区分で色分けします
  (「不一致のルールのみ表示」で絞り込み可)。不一致が解釈差異か計算ミスかは自動判定しません。
  - 完全一致 / 意味的一致 (`3750` と `"3,750"` など) / 動作結果の不一致 / 適用可否の不一致 (一方だけ「適用不可」) / 生成失敗・形式不正

`results.json` の `generation_method` が `common_framework` になり、従来方式 (`conventional`) と区別できます。

結果を保存するたびに、Excel / pandas でそのまま集計できる CSV (UTF-8 BOM 付き) を書き出します。

| --- | --- | --- |
| `summary.csv` | 仕様 × 生成モデル | 番号・テーマ・解釈揺れ・方式・framework_id・状態・error_kind・時間・トークン数 (推論含む)・検証エラー数・適用不可のルール数・判定区分ごとのルール数 |
| `rule_results.csv` | 仕様 × ルール × 生成モデル × 動作項目 (ロング形式) | rule_id・条件値 (`YNYY`)・条件 (`C1=Y; …` と条件文)・値・返ってきた生の値・判定区分 (完全一致 / 不一致など) |

## 14. API エラー時の停止と再実行

- OpenRouter から **APIキーの利用上限超過・残高不足** (`Key limit exceeded` / `total limit exceeded` /
  HTTP 402 / 上限超過を示す HTTP 403) が返ると、一括実行は新しい仕様・新しいリクエストの送信を止めます。
  処理中だった仕様の成功結果は保存され、未実行の仕様は `batch_summary.json` に `skipped_key_limit` と記録されます。
  一般的な HTTP 403 (モデレーション等) や 429 (レート制限) では止めません。
- **成功済みの結果を再利用**: 成功した抽出・生成結果は `outputs/_cache/` に保存され、再実行時に
  「モデル + 実際に送るプロンプト全文 (要求仕様・プロンプト・抽出項目・共通DT枠組みを含む) + 生成方式」が
  完全に同じ場合だけ再利用されます。つまり上限超過後に再実行すると、失敗・未実行の処理だけが API に送られます。
  同じ条件でサンプリングし直したい場合は、一括実行ダイアログまたはモデル設定でチェックを外してください。

処理の流れを追うときは `services/experiment_runner.py` と `services/batch_runner.py` の
`run()` を読むのが早道です (どちらも `services/step_runner.py` を介して抽出・生成を行います)。
比較機能の計算ロジックを追うときは `services/table_comparison.py` の
`align_labels()` → `compare_tables()` の流れを読むのが早道です。

## 今後の拡張について

- 複数実行 (別日時の `outputs/` フォルダ) をまたいだ比較は未対応です。現状は
  1回の実行内 (同じ Requirements + 同じ Decision Items から生成した複数モデル) の比較のみです。
- 不完全性判定 (条件の組み合わせの網羅漏れなど) は未実装です。
- 複数実行結果の読み込みは `utils/file_manager.py` の `list_output_runs()` / `load_experiment_record()`
  が既にあるので、それを使って `results.json` を読み込めます。
